### 3.2 Deterministic routing categories

Root operation selectors/special actions currently exposed by source are:

- `--init`: select Init; selector-only in a TTY opens the Init configuration
  wizard;
- `--login`: launch the guided direct-API credential configuration action;
- `--splash`: play the canonical splash and exit;
- `--ver`/`--version`: informational version actions.

Other workflows use subcommands (`ai-context`, `plan`, `evolve`, `review`) or

Presentation modifiers used by root/Init routing are:

- `--dashboard`;
- `--no-splash`.

Presentation modifiers alone do not select direct Init. In particular,
`rb-harness --dashboard` in a TTY opens the root wizard with dashboard intent.

The canonical Init operational inputs are exactly:

- positional `[request...]`;
- `--profile <profile-id>`;
- `--file <path>`;
- `--credential <id-or-label>`;
- `--project <path>` (default `.`);
- `--headless`;
- `--timeout <seconds>` (default `120`, valid `1..900`);
- `--dashboard` as its presentation option.

For `--init` routing, `--project`, `--profile`, `--credential`, `--file`,
`--headless`, `--timeout`, help, or positional request text imply direct

exact missing-input list and points back to `rb-harness --init`.

The Init configuration wizard and the semantic interview are separate layers:

- the configuration wizard chooses project, exact profile, request source,
  optional direct-API credential, dashboard, and whether to execute;
- the semantic interview resolves material product/architecture ambiguity
  after the intent semantic operation.

Direct CLI mode bypasses only the configuration wizard. In an interactive TTY
it still performs the semantic interview unless `--headless` is supplied. A
non-TTY direct invocation also uses the non-interactive recommendation policy,
even without an explicit `--headless`, because no answer channel exists.

never hangs: routing prints help and fails with deterministic guidance. Source
authority: `packages/core/src/init-routing.ts`; regression authority:

## 6. Semantic pipeline

The dashboard projects the canonical pipeline as:

```text
pedido -> intent -> entrevista -> decisões -> work -> closure
```

These labels combine semantic operations with orchestration/presentation
stages:

| Dashboard stage | Run-state stages | Nature |
|---|---|---|
| `pedido` | `request-received` | orchestration: bind request/profile/run evidence |
| `intent` | `intent-requested`, `intent-decoded` | **semantic operation**: generate/decode intent IR |
| `entrevista` | `interview-pending` | orchestration plus user/policy authority selection |
| `decisões` | `intent-resolved` | deterministic resolution of request/interview authority |
| `work` | `work-requested`, `work-resolved` | **semantic operation**: generate/decode work IR |
| `closure` | `deterministic-closure`, `published` | deterministic Core validation, rendering, manifest closure, and publication |

A healthy no-correction run therefore has two semantic operations: intent and
work. Interview/resolved authority is not a third model call. Closure performs
zero provider, adapter, formatter, repair, or provider-specific calls.

## 7. Interview model

Every material proposed question has:

- a stable semantic key and concrete question;
- one concrete selectable `Recommended` value;
- a useful `Why`/rationale;
- zero or more concrete alternatives.

`formatInteractiveQuestion()` renders those four parts and explicitly says a
blank answer accepts the recommendation.

Selection behavior:

- nonblank interactive response -> `explicit` acceptance and `user-answer`
  authority;
- blank interactive response -> exact recommended value,
  `blank-interactive`, and `accepted-recommendation` authority;
- headless/non-interactive policy -> exact recommended value,
  `non-interactive-policy`, and `accepted-recommendation` authority.

Accepted recommendation is a distinct, Core-verifiable provenance kind. It may
resolve a RIGID product or architecture decision because the recommendation was
materialized as a question before selection. A vague recommendation such as
“use a suitable database” is rejected.

Silent model defaults cannot establish RIGID product/architecture authority.
Core emits I-17 for a `model-default` that tries to decide such a determination.

Question count is not fixed. The intent slice emits the set of material
questions, every one is persisted before selection, and execution proceeds
only after all emitted questions resolve and `ensureIntentSufficient()` accepts
the intent. The current interview is one intent-generated batch traversed
question by question; it is not the older standalone adaptive-round engine.

Evidence: `packages/core/src/vnext/interview.ts`,
`packages/core/src/vnext/init.ts`, and interview regressions in
`packages/core/test/vnext/phase3-init.test.ts`.

Authority semantics:

- accepted recommendations retain the exact selected value plus
  `blank-interactive` or `non-interactive-policy` proof;

rejected snippets are orchestration/debug evidence only. They are not fields of
`InitProjectModel` and are never a substitute for request/user/accepted-
recommendation authority.

  `packages/core/src/vnext/path-contract.ts`;

## 11. SemanticKey contract

The exact pattern is:

```text
^[a-z][a-z0-9-]{1,47}$
```

`SEMANTIC_KEY_PATTERN` in `packages/core/src/vnext/identity.ts` is the shared
authority. Provider schemas import it, wire decoding calls `semanticKey()`,
resolution validates declarations/references, and Core validates canonical
models against the same grammar.

Keys are model-authored semantic references, not machine execution IDs. Core
derives `R-001`, `P01`, `T001`, `AC-T001-01`, and artifact IDs after semantic
resolution.

## 12. `ownedPaths` contract

The exact shared pattern authority is
`PROJECT_RELATIVE_PATH_PATTERN` in
`packages/core/src/vnext/path-contract.ts`:

```text
^(?![A-Za-z]:/)(?!(?:\*|\*\*|\*\*/\*)$)(?:(?!\.{1,2}(?:/|$))[^/\\\u0000\n\r\t`]+)(?:/(?:(?!\.{1,2}(?:/|$))[^/\\\u0000\n\r\t`]+))*$
```

Supported forms are:

- an explicit project-relative file, for example `package.json` or
  `src/domain/service.ts`;
- a project-relative directory token without a trailing `/`, for example
  `migrations` or `src/domain`; directory ownership covers its subtree;
- a bounded glob below a project-relative root, for example `src/**/*.ts`.

Rejected forms include:

- absolute paths and Windows drive roots;
- backslashes;
- empty, `.` or `..` segments;
- NUL, newline, carriage return, tab, or backtick;
- trailing `/` directory syntax;
- project-wide unbounded `*`, `**`, or `**/*`.

Independent Core rules also reject intersections with `.rb`, `.rb-harness`,
`.git`, and any authoritative protected path. Provider schema, work decoder,
and Core all use the same syntax authority and fail closed. Current regressions
prove valid `migrations`, `src/domain/destinations`, `tests`, `src/**/*.ts`, and
`package.json`, and reject their trailing-slash forms plus unsafe traversal and
global globs.

## 13. Quality commands and validation intents

First-pass quality commands must:

- be an actual one-line executable command;
- run non-interactively;
- terminate by themselves;
- return their real exit status;
- not mask failure with `|| true`, `; true`, or forced `exit 0`.

They must not be development/application servers, watchers, long-running
workers, or interactive processes. The prompt and deterministic validator
explicitly reject representative server/watch commands and flags. The
`QualityCommandKind` value `run` does not make a long-running command valid.

Current validation kinds are a closed union:

- `command`: executor runs an exact declared quality-command key and observes
  completion/exit status;
- `manual`: executor performs a non-command inspection or action; executable
  shell prose disguised as manual is rejected;
- `human`: evidence genuinely requires human judgement/intervention unavailable
  to the executor.

Provider wire uses `{kind, value}` and Core resolves it to the typed variants in
`ir.ts`. Rendering emits backticked commands, `manual: ...`, or `human: ...`.

## 14. Visual acceptance and I-13

Final invariant: I-13 positively identifies unsupported explicit visual or
aesthetic semantics. Neutral UI vocabulary is not inherently visual.

Functional UI acceptance is valid when it states deterministic behavior,
state, or data, including:

- application or DOM state;
- navigation;
- form submission;
- an exact count, value, or message;
- filtering or sorting;
- authorization-dependent enabled/disabled action state;
- an API/HTTP effect observable through UI behavior;
- deterministic state transitions.

Unsupported explicit visual semantics remain invalid as canonical Init
acceptance boundaries:

- styling and colors;
- spacing;
- visual prominence or distinction;
- positioning/alignment as appearance;
- screenshot/pixel comparison;
- responsive/geometry/rendered-motion proof outside the current semantic
  model;
- visual fidelity and aesthetic/layout judgement.

Mixed functional plus explicit aesthetic acceptance remains invalid. Genuine
visual judgement may be separated into a `human` validation while acceptance
stays functional.

At the Phase 3.5 freeze, the old language-sensitive
`STRONG_VISUAL_CRITERION`/`UI_SURFACE`/weak-verb rescue architecture was removed.
It had produced false positives from neutral words such as screen, panel,
display, render, visible, and hidden. The current
`AESTHETIC_VISUAL_BOUNDARY` plus
`UNSUPPORTED_RENDERED_VISUAL_BOUNDARY` in
`packages/core/src/execution-contract.ts` identifies the unsupported semantics
instead of trying to whitelist functional language.

Real purchasing-flow dogfood supplied the Portuguese regressions now in
`packages/core/test/execution-contract.test.ts` and
`packages/core/test/vnext/validation.test.ts`: counts, 403/list-empty behavior,
self-approval disabled state, filtered navigation/listing, dashboard exact
counts, and rejection/correction state transitions do not emit I-13. Explicit
layout/visibility and “visually prominent in red” still do.

## 15. Current recovery architecture and budgets

The current source values in `packages/core/src/vnext/gateway.ts` are:

| Budget | Current value |
|---|---:|
| corrective regenerations per slice | 1 |
| corrective regenerations per run | 2 |
| semantic operations per run | 4 |
| transport invocations per run | 6 |
| transport retries per semantic operation | 1 |
| transport retries per run | 2 |

These are currently hard-coded guards in `beginOperation()`/`invoke()`, not one
exported budget object. The proposed increase has **not** been implemented.

Recovery semantics:

- regenerate one complete intent or work slice;
- apply every violated rule globally across the regenerated slice;
- treat prior pointers as evidence from the rejected attempt, not patch
  targets;
- bind the authoritative original request and, for work, the complete resolved
  intent/interview authority;
- never partially patch a provider candidate;
- never run a JSON formatter/fixer;
- never repair Markdown;
- never splice documents;
- never fall back to another provider/profile/transport.

The canonical semantic engine may canonicalize an already decoded Core model,
but it never repairs missing/invalid model semantics. Recovery is another
bounded semantic operation for the whole slice.

## 17. Recovery rule ledger

closed vocabulary:

1. `acceptance-no-visual-only`;
2. `acceptance-self-contained`;
3. `requirement-coverage`;
4. `validation-command-executable`;
5. `validation-command-terminating`;
6. `task-completeness`;
7. `rigid-decision-requires-authority`;
8. `semantic-key-valid`;

Rules are derived from provider-neutral wire/Core findings. A `Set` preserves
first-finding order and deterministically deduplicates rules. Unknown findings

generic Core guidance.

All rules in a correction apply to the whole regenerated slice. Specific
findings are diagnostic context, never localized patch instructions.

Remaining minor technical debt: `recoveryRule()` still maps several rules by
matching current finding message prose/substrings plus pointers. The vocabulary
is closed and tested, but this mapping is not yet entirely code-based finding
metadata. Do not expand it casually; a future cleanup should add typed finding
codes without changing model-facing semantics.

## 18. Recovery observability

`RecoveryAttemptEvidence` is defined in
`packages/core/src/vnext/run-state.ts` and persisted inside:

```text
.rb-harness/runs/<runId>/vnext-init-state.json
```

Each corrective attempt records:

- semantic `slice` (`intent` or `work`);
- semantic-operation `ordinal`;
- recovery scope flags proving complete-slice regeneration, global rule
  application, and previous-pointer evidence;
- deduplicated violated rules;
- sanitized specific prior findings (`pointer` plus model-facing guidance);
- SHA-256 of the original request;
- SHA-256 of authoritative input;
- for work, SHA-256 of resolved interview authority;
- SHA-256 of the recovery context;
